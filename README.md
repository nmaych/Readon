# Readon

一个简洁的 Android 阅读器。书籍来自 GitHub 仓库，在线阅读或下载到本地，界面遵循「主页 / 书架 / 设置」三栏结构。

当前版本 **1.0.10**（versionCode 10010）。

## 功能

### 主页 —— 在线书库
- 从 GitHub 仓库递归列出所有可读文件，按文件夹自动分类（如 `默认/xxx.txt`）
- 支持格式：`txt`、`md`（及 `markdown` 别名）、`html`、`epub`；`pdf` 提示下载后用系统应用打开
- **在线阅读**：点书即读，无需下载。先取 **2 MB 前缀**（约七十万字）立刻显示，剩下的在
  后台按区间续传，读完前缀前就补齐；补齐后原地替换成完整正文，阅读位置不变
- **在线阅读缓存**：读过的书会在设备上留一份，再次打开不再重新下载。它与书架数据**完全分开**——
  存在缓存目录、单独统计占用、单独清理（设置 → 存储），上限 512 MB 并按最后阅读时间淘汰。
  命中要求大小与仓库一致，所以上游换过文件不会被旧缓存顶掉
- **列表里标出「已缓存」**：已经留在缓存里、点开即可离线阅读的书会显示一条标记，和「已在书架」
  用不同颜色区分——书架是用户主动保存的，缓存只是读过一次留下的副本，系统可能回收。标记只用
  目录与大小判断，**不会刷新缓存的最后阅读时间**，因此浏览列表不会改变淘汰顺序
- **下载**：点右侧下载图标保存到设备，带百分比进度，出现在书架；下载在应用级作用域运行，**切到书架或设置也不会中断**。
  已下载的书再在主页点开时**直接读设备上的文件**，不会再请求网络，也不会在阅读缓存里多存一份
- **已缓存的书点「下载」不再重新下载**：缓存里那份完整副本会被**移动**到书架（同属应用私有
  存储，因此是一次 rename），登记后删掉缓存条目；只有确实没有可用副本时才走网络。判断用的是
  移动那一刻的文件状态，而不是列表上几分钟前算出的标记——缓存可能已被系统回收或被设置页清空。
  rename 失败时退回复制再删除，两条路都不通就保留缓存并照常下载
- **浏览记忆**：记住搜索词、分类筛选和滚动位置，切到别的标签页或重启应用后回来原样恢复。
  记忆跟着「它属于哪个书库」一起存，换了仓库不会把上一个仓库的搜索词带过来（那会显示成满屏
  「没有匹配的书」）；记住的分类若已被改名或删除则丢弃而不是恢复。写入走不触发设置变更的
  静默通道，否则保存滚动位置会被主页当成「设置变了」，反过来每次都重新拉一遍书库
- 书库列表在应用级缓存：切换标签页不会重新拉取，只有仓库 / 分支 / 令牌 / 线路改变或手动刷新时才会重新获取
- 搜索书名 / 分类；顶栏显示当前仓库与分支；可配置访问令牌以提升 API 限额
- 搜索或分类筛选生效时，顶栏出现一键清除，同时清掉两者

### 书架
- 本地已下载书籍的封面网格，封面按书名哈希生成渐变，同一本书永远同一张封面
- 阅读进度百分比直接画在封面上；从阅读器返回或下载完成时自动刷新
- 每本书显示已读章节数与上次阅读时间（`23% · 12/340 章`、`上次阅读：今天 14:30`）。章节总数由阅读器在建目录时记录，书架不必为此重新解码整本书；从未打开过的书不显示这两项，而不是显示 `0/0` 或 1970 年
- **封面有上限，不是越大越好**：列数由 `Adapt.shelfColumns` 从**目标宽度**（96 dp）算出，
  再用 78 dp 的地板兜住（更窄会截掉两行书名）。内容列先按 `Adapt.contentWidthDp` 封顶
  （与主页列表同一个上限），剩下的宽度变成两侧等宽边距，所以在**任何窗口**上封面都是
  90–105 dp：一部 411 dp 手机排 4 列、每本约 90 dp，1200 dp 的平板排 8 列而不是把封面放到
  284 dp，320 dp 的窄屏也仍有 3 列。此前用的 `Adapt.gridColumns` 只能回答「至少 116 dp 时最多
  几列」——那永远是最小的合法列数，于是 411 dp 上只有 3 列、每本 126 dp，书架看着像三张海报
- **从本地导入**：右上角「+」一次可选多个文件，导入 `txt` / `md` / `html` / `epub`。文件流式复制进应用存储，大文件不会占用整块内存；多选导入在应用级作用域运行，切换页面不会中断
- 排序：最近阅读 / 最近添加 / 书名 / 分类；长按封面删除（删除按钮不再占在每一格上）
- 封面列数随窗口自适应（`Adapt.shelfColumns`），**有上限**：`GridCells.Adaptive` 在 1200dp
  上会排出十一列，那不是更大的书架，而是标题看不清、行太长扫不了的缩略图墙

### 阅读器
- 正文用 Compose 原生排版，所见即所量：分页与渲染同一套测量
- 加载时显示当前阶段（连接线路 / 下载进度 / 排版），失败会说明原因并可重试或返回，不会停在「正在排版」
- **两种阅读方式**：左右翻页（左 1/3 屏上一页，右 1/3 屏下一页，中间点按呼出/隐藏工具栏），或上下滑动的连续滚动。滚动模式按空行切段交给 `LazyColumn`，百万字长篇只测量可见部分
- **两种模式共用同一个字符偏移**，所以切换模式、改字号、跳目录都不会丢失位置
- **自动阅读**：底部开关按设定间隔自动翻页（滚动模式则**连续缓慢滑动**），间隔在设置里调
  （3–60 秒，默认 15 秒）。到最后一页会停下而不是绕回开头，点一下正文即暂停；开关跨书
  记住，但每本书第一次打开总是暂停的
- **顶部留白**：正文上方固定留出「显示挖孔 + 状态行高度」——阅读时状态栏是**关掉**的，
  所以留白是真正的空白，而不是「让开一个一直在那儿的栏」；挖孔是硬件遮挡，刘海 / 挖孔屏上
  第一行也不会落到摄像头下面。这段留白不随工具栏显隐变化，分页高度也同步扣除
- **阅读时隐藏状态栏与导航栏**：打开书就收起手机上下两条系统栏，退出时恢复；从边缘划一下
  可以临时调出（不彻底隐藏，保留出路）。**从别的应用切回阅读界面时会重新收起**——Android 在
  窗口重新获得焦点时会自己把系统栏放回来，所以除了进入时隐藏，还在 `ON_RESUME` 与窗口重新
  获得焦点时各隐藏一次；否则切出去再回来，手机上就又是那两条栏
- **阅读器自绘状态行**（状态栏被关掉之后，这两行就是唯一的时钟和电量）：
  - 上方一行显示**当前章节名**，用阅读主题的颜色和字体；工具栏弹出时淡出（同一位置会有
    更大字号的同名章节，两份叠在一起像渲染错误）
  - 下方一行**左边是「第 12 / 340 章 · 23%」、右边是时间和电量**；进度与进度条取自同一个
    fraction，电量只在**低电且未充电**时变红。时钟对齐到下一分钟刷新，电量走
    `ACTION_BATTERY_CHANGED` 的 sticky 广播，两者在离开阅读器时注销
  - **这两行占的位置就是正文让开的位置**：`ReaderHud.band` 由字体换算后的行高
    （`18.sp.toDp()`，`sp` 本来就带着字体缩放）算出完整带高，正文按它内缩、状态行在
    同一条带子里绘制。1.0.9 是按 18 dp 预留、按 18 sp 绘制——系统字号 1.3 倍时文字有
    23 dp 高却只占 18 dp 的位置，于是章节名与时间电量盖住了每页的第一行和最后一行
- 自动识别章节（`第X章`、`Chapter N`、`楔子/序章/尾声`、Markdown 标题），侧滑目录直达
- 全书全文搜索，逐条跳转
- **书签**：底部一键标记当前位置，底部列表可跳转 / 重命名 / 删除；未命名的书签显示该处正文摘要
- **书签与目录都在下方工具栏**，紧挨着「第 12 / 340 章」和进度条——按钮放在「你在哪」的旁边，
  才看得出它作用于当前位置。顶栏只留返回 / 搜索 / 阅读设置，因此**章节名有空间完整显示**
  （可折两行再截断，而不是被挤成「第一章…」）
- **返回键按层关闭**：先关书签列表 → 搜索框 → 目录 → 阅读设置，都关掉才离开这本书。在
  主页 / 书架 / 设置之间，返回键先回主页，再按才退出应用
- **阅读界面内的快速设置**：字号、行距、字体、主题、文字与页面颜色、阅读方式，都不用离开正文
- 阅读主题：纸白 / 米黄 / 护眼 / 夜间 / 纯黑；字号 12–30sp；行距 1.2–2.4
- **字体**：宋体 / 黑体 / 等宽 / 楷体
- **文字颜色与页面颜色可各自独立选择**，覆盖主题；次级文字（页脚、副标题、搜索摘要）会按这对颜色重新推导，保证仍然可读
- 阅读位置以字符偏移保存，改字号后仍停在同一句话
- **正文列宽随屏幕自适应**：正文列宽上限 720dp（约 40 个汉字），左右边距由剩余空间平分。
  平板上不会出现「一行七十多个汉字」那种找不到下一行的排版；手机上边距仍是原来的 22dp，
  一行不变。这里约束的是**列宽**而不是边距——只限制边距的话，2560dp 窗口上仍会留下 2000dp
  以上的正文
- 章末的连续空行不会变成空白页：每页都从第一个非空白字符开始
- TXT 自动检测编码（UTF-8 / GBK / UTF-16，含无 BOM 情况），采样会同时看文件头部与中段，避免「ASCII 开头 + GBK 正文」被误判为 UTF-8
- 翻页按需分页，整书不预排版，百万字也秒开

### 设置
- 阅读偏好（阅读方式、字体、主题、文字/页面颜色、字号、行距、屏幕常亮、**自动阅读与翻页间隔**）
- 应用主题：跟随系统 / 浅色 / 深色
- 书库来源：GitHub 用户名 / 仓库 / 分支 / 访问令牌，全部可改
- **网络线路**：显示当前实际生效的线路，可手动指定，可点「检测线路」逐条测试
- 存储：查看占用、清空本地书籍、**单独清理在线阅读缓存**
- 更新：从 GitHub 检查新版本，下载并校验 SHA-256 后安装。检查在应用级作用域运行，切换标签页不会中断或重来；失败不会记入「上次检查」，因此网络恢复后可以立刻重试。**清单与 releases API 每次都会同时查**，取较新的那个答案——只信清单会让一份过期的清单被当成「已是最新版本」。**更新说明按 Markdown 渲染**（标题、嵌套列表、行内代码、链接），放在卡片里一个**固定最大高度、自己滚动**的框里——整段说明都在，但不会把「下载更新」按钮挤出屏幕；只有内容真的溢出时才提示可以上下滑动
- **安装完成后清理安装包**：更新包约 11 MB，留在 `cacheDir/updates`。应用启动时（IO 线程）删除它——启动是唯一能确认安装成功的时刻，因为安装器替换的就是应用自己的代码，旧版本在用户点「安装」后再也不会运行。文件被安装器占用时删不掉，留给下次启动，不当作错误上报
- **链接**：项目主页 / 全部版本 / 问题反馈 / 默认书库，点一下在浏览器中打开
- 关于：版本信息

## 网络线路

`raw.githubusercontent.com` 在部分网络下被完全阻断（连接超时后 TLS 重置）。因此所有请求都同时向多条线路发起，取最先成功的，并记住可用线路。

| 线路 | 小文件 | 大文件（>20 MB） | 列表接口 |
|------|--------|------------------|----------|
| GitHub 直连 | 超时 | 超时 | 可用 |
| cdn.jsdelivr.net | 可用 | 403 | 403 |
| fastly / gcore.jsdelivr.net | 可用 | 403 | 403 |
| ghproxy.net | 可用 | 可用 | 403 |
| gh-proxy.com | 可用 | 可用 | 可用 |
| ghfast.top / gitmirror / Statically | 超时 | 超时 | — |

实测数据来自本仓库（53 本书，33 本超过 8 MB，最大 75 MB）。jsDelivr 限制单文件 20 MB、整包 50 MB，所以它无法覆盖这个书库；`ghproxy.net` 与 `gh-proxy.com` 才能。

因此：
- **列表**与**取文件**用两套独立的线路表——`api.github.com` 与 `raw.githubusercontent.com` 是两个不同的服务，前者没被阻断时后者可能已被阻断。
- 选线路先用 **2 KB 的 Range 请求探测**，再流式传输，避免把几十兆的文件在九条线路上各试一遍。上次成功的线路会被**单独先探一次**，所以网络正常时每次打开书只有一个 2 KB 请求，而不是每次都跑九条线路。
- 探测和竞速的请求都是**可取消**的：选出赢家后，其余请求立即断开，不会留下十几条连接空等到超时。小请求（列表、清单、探测）用 8–25 秒的整调用超时，大文件传输用 10 分钟——「线路没反应」应当很快变成一条能读的错误，而不是让界面一直转圈。
- 在线阅读的文本**先按区间取回一部分再解码**：2 MB 前缀足够读到后台补齐为止，因此峰值内存
  只有一个字符缓冲，首屏等待也不再等于整本书的下载时间。区间不被遵守（线路返回 200 而不是
  206）时会退回整本下载；EPUB 因为需要随机访问 zip，仍然整块取回，上限 64 MB

`tools/check_ranges.py` 对着线上书库逐条线路验证 `Range` 是否真的被遵守——「先下载一部分」
这个功能的前提是可以被验证的，而不是假设的。当前实测：这个书库里唯一能扛住 75 MB 文件的
两条线路 `gh-proxy.com` 与 `ghproxy.net` 都返回 206 并报出真实大小。

## 书库格式

任意公开 GitHub 仓库，文件夹即分类：

```
仓库根/
├── 默认/
│   ├── 书名.txt
│   └── 另一本书.epub
├── 科幻/
│   └── 三体.txt
└── ...
```

默认书库：`nmaych/ReadonBooklibrary`，分支 `main`。全部可在设置中修改。

## 构建

需要 JDK 17、Android SDK 34、Gradle 8.7。依赖已全部落在本地 Gradle 缓存中，支持离线构建：

```
build.cmd                # assembleDebug
build.cmd assembleRelease
```

发布前运行仓库自检：

```
check.cmd                        # 工作流、版本号、清单、.gitignore、书籍逻辑
tools\check-book-logic.cmd       # 编码检测、章节切分、分页与书架标签（桌面运行，无需设备）
tools\verify_release.py          # 校验 dist/ 里的 APK 与清单是否自洽
```

`tools\check-book-logic.cmd` 直接编译 `TextCodec.kt`、`Chapters.kt`、`PageCursor.kt`、
`TextFlow.kt`、`ReaderInk.kt`、`Bookmarks.kt`、`OnlineCachePolicy.kt`、`PartialRead.kt`、
`AutoRead.kt`、`Markdown.kt`、`UpdateDecision.kt`、`Model.kt` 与 `ShelfLabels.kt` 这几个纯
JVM 文件（不复制
源码，避免与线上代码脱节），覆盖
UTF-8/GBK/UTF-16、BOM、「ASCII 开头 + GBK 正文」这类会导致乱码的边界，章节切分的连续性与性能，
分页游标的「第一页不能对着空列表取 last」回归，**章末空行不再产生空白页**（用真实测量模型：
行高按可视行数算，并断言旧逻辑确实会产生空白页，否则说明测试已失效），**滚动分段**（段落切分、
长段上限、偏移定位与线性扫描一致），**阅读配色的对比度保证**（120 组页面/文字配色组合，次级
文字都必须达标），**书签**的摘要提取、去重与前后跳转，**在线阅读缓存**的命中判定（大小不符 /
截断 / 空文件都不算命中）与 LRU 淘汰边界，**自动阅读的夹紧规则**（0 秒 / 负数 / 超大值都必须
落到 3–60 秒；任何输入都要产生正的等待时间，否则定时器会变成忙循环；标签与实际等待必须来自
同一个夹紧）与**滚动模式的缓慢滑动**（滑动时长必须等于间隔，即整段都在动；默认速度必须
< 100 dp/s，并断言旧行为会超过 1000 dp/s），**更新说明的 Markdown 解析**（60 项：标题 /
嵌套列表 / 有序列表 / 引用 / 围栏代码 / 分隔线，行内粗体、斜体、删除线、代码与链接，
`**`Content-Range` 的解析** 这类嵌套，列表项的缩进续行必须并入该项（断言「解析出的最长
列表项 > 最长源行的两倍」，折行错误下每项恰好只有一行长，这条过不去），未闭合与空标记
必须保留为文本，以及用**真实的
`dist/update.json` 说明**断言「源里的列表项数量 = 解析出来的数量」），**部分下载的判定**
（`Content-Range` 解析，含「有区间但没报大小」的 `*` 写法；
大小未知时不敢断言完整；前缀长度的选择；只去掉末尾那一个替换字符，正文中间的保留），
**更新检查两个来源的合并规则**（过期清单说「已是最新」而 releases 有新版本时必须提示更新，
且与两个来源的返回顺序无关；无法安装的新版本优先于「已是最新」；`versionCode` 算术
`1.10.0 > 1.9.0`），还有书架标签的「昨天是日历天而不是 24 小时」等日期边界。离线 Gradle
缓存中没有 JUnit jar，所以这些检查放在这里而不是单元测试里。

`TextFlow`、`ReaderInk`、`Bookmarks`、`OnlineCachePolicy`、`PartialRead`、`AutoRead`、
`Markdown` 与
`UpdateDecision` 之所以刻意不含 Android 与 Compose 类型，正是为了让这条检查能覆盖它们：
空白页、配色可读性、缓存了错的书、缓存无限增长、把截断的书当成完整的书、自动阅读失控、
更新说明里悄悄少掉一个列表项，
以及「两份互相矛盾的更新答案该信哪一个」，都是那种「在设备上要肉眼翻很多页、或者用很久
才发现」的问题。

`PageCursor` 之所以从 `Paginator` 里拆出来，正是为了让这条检查能覆盖它：1.0.2 打开
任何一本书都闪退，根因就是分页器用空列表取 `last()`，而那段代码在 Compose 的
`remember { ... }` 里，加载器的 `try`/`catch` 包不到它。同理，`OnlineCachePolicy` 从
`OnlineCache` 里拆出来，`UpdateDecision` 从 `UpdateManager` 里拆出来：策略能独立于文件 I/O
和网络出错。

发布版签名密钥位于 `keystore/readon-release.jks`，凭据在 `app-project/keystore.properties`（不入库）。

发布新版时改 `app/build.gradle.kts` 里的 `appVersionCode` / `appVersionName`，构建后：

```
build.cmd assembleRelease
copy app-project\app\build\outputs\apk\release\app-release.apk dist\readon-1.0.10.apk
python tools\ci_release.py --name 1.0.10 --apk dist\readon-1.0.10.apk
python tools\verify_release.py
```

`ci_release.py` 会用实际产出的 APK 重算 SHA-256、写好下载地址，并从 CHANGELOG
提取该版本的说明写入 `dist/update.json`——手改哈希会让应用判定更新包损坏，手改
说明则会让 GitHub release 页面和应用内提示不一致。`verify_release.py` 独立复算
一遍（不 import 发布脚本），确认哈希、版本号算术、下载地址和说明都对得上。

## 更新机制

1. 应用内「设置 → 更新」同时读取 `dist/update.json` 与 GitHub releases API（都走多线路），
   取**较新**的那个答案。只信清单是 1.0.5 修掉的 bug：清单过期时会谎报「已是最新版本」
2. 两个来源都带 `no-cache` 头，并在 URL 上追加时间戳，避免代理缓存住旧清单
3. `versionCode` 高于当前版本即提示；比对始终用 versionCode，不用版本名字符串
4. 下载到应用私有缓存，逐块回传进度；有 `sha256` 则校验，不匹配直接删除
5. 调系统 PackageInstaller 安装；首次需要用户在系统里授予「安装未知应用」权限

## 图标

`art/original-icon.png` 是设计原图，不重绘。`tools/make_icon.py` 只做派生：各密度 PNG、圆形版本，以及自适应图标前景（背景取原图自身的深蓝色，因此任何启动器裁切形状下都不会露出白边）。
